# UX / UI Specification

## Navigation — IMPLEMENTED
Compose navigation between **Map, Journey, Progress and Profile** is implemented in `WorldDiscoveryApp`, including the bottom navigation bar and destination routes. This status covers navigation infrastructure, not feature completeness.

## Map
**PARTIALLY IMPLEMENTED, physically validated where noted (Samsung device; see `PROJECT_STATUS.md` §17 and `ARCHITECTURE_DECISIONS.md`'s "Map rendering engine" entry for the itemized record):** `MapScreen` renders MapLibre Native with the user's discovered H3 cells, consumed reactively from Room (`DiscoveredCellRepository.observeAll()` → derived cell geometries), alongside the existing user-triggered current-location test action, which is preserved unchanged. Physically validated on-device: MapLibre core rendering; the current `https://tiles.openfreemap.org/styles/liberty` style loading (a temporary validation style, not a final provider/product choice — it replaces the earlier `demotiles.maplibre.org` placeholder); H3 cell rendering; the current-position marker; mainland France's OSM-derived visited-country fill; OpenMapTiles water-layer coastline masking; the OpenMapTiles FRA terrestrial boundary line; and Android bundled rendering-resource loading. Still genuinely pending/not final: the final tile/style provider, final style, hosting strategy, offline packaging strategy, final visual direction, and physical antimeridian-crossing rendering (the unwrapping math itself is unit-tested; no physically-validated location crosses ±180°) — these remain **ENGINEERING DESIGN REQUIRED** or **NEEDS USER CONFIRMATION** as already tracked, not silently assumed working. The map is otherwise read-only for this increment: no clustering, Progress overlays, or ELIGIBLE/RESTRICTED_EXCLUDED/UNKNOWN handling. (Corrected wording: the current France prototype's camera/focus system is not limited to Country level — it supports focus through Country → Region (Admin1) → Department (Admin2), with click-to-focus navigation and a unified Back stack across all three levels; see the Country → Region → Department paragraph below.) **DECIDED / NOT IMPLEMENTED:** Map is the primary surface and visualizes discovered territory rather than a raw GPS breadcrumb trace; Certified and Non-certified remain distinguishable where exposed — currently via a provisional fill color, not final art direction; labels/borders are contextual only; visited/present country styling means **VISITED / PRESENCE, never fully explored, 100% completed, or full geographic coverage** — exact exploration remains derived solely from canonical H3 discovery data. **Country → Region → Department (France, full metropolitan coverage) is now IMPLEMENTED; physical validation FAILED once early on, corrections landed, and functional hierarchy behavior has since PASSED physical validation** (see `PROJECT_STATUS.md`'s Phase H — Round 4 correction round, and Phase FH-1 for the department-coverage completion and its own "second physical validation" entry): Region/Department visited overlays, click-to-focus navigation, and a unified Back stack across all three levels — real OSM-derived data (13 metropolitan regions, all 96 of their departments including Corse's two), never hand-drawn; physical validation sampled both a visited branch (Nouvelle-Aquitaine/Haute-Vienne, existing behavior confirmed still functional) and an unvisited branch (Grand Est and one of its departments, confirming unvisited administrative areas are genuinely navigable) — this is functional navigation validation, not individual physical testing of every one of the 13 regions/96 departments, and not final visual/design validation (labels, contrast, zoom thresholds, basemap remain future work); everything below Department (local discovery areas, H3) remains future work. **Color hierarchy is SELECTION-RELATIVE, not a fixed per-level rule.** The originally-implemented rule (Country darkest, Region medium, Department lightest, unconditionally) was physically tested and rejected — it did not match the approved reference design and is no longer authoritative. The current, corrected rule: whichever geographic level is currently selected renders as the lightest, richest orange (`GeographicAreaStyleRole.SELECTED`, `#FFA23A` starting value); the level directly below it renders one step darker (`DIRECT_SUBLEVEL`, `#C96A16`); every ancestor, unselected sibling, or more-distant level renders in the darkest, most subdued tier (`ANCESTOR_CONTEXT`, `#7A3D16`) so it never visually competes with the active selection. The same Region therefore renders differently depending on context — darker while merely a sub-level beneath a selected Country, light the moment that Region itself becomes selected. Discovered H3 cells keep their own, already-validated Certified/Non-certified color scheme, deliberately untouched by this rework (see `PROJECT_STATUS.md`'s Round 4 entry for why swapping it for a fourth "discovery orange" was judged too large a regression risk for this round and left as an open question instead of decided silently). Selecting the Country level from any focus depth (Region or Department) is now possible and always clears any deeper Region/Department focus; the camera unconditionally re-fits to the newly selected geography's own bounds on every successful selection, regardless of prior manual pan/zoom. **Department-level derived first-discovery corridor is now IMPLEMENTED (corrected after Codex review), NOT PHYSICALLY VALIDATED until the next Samsung test** (see `PROJECT_STATUS.md`'s Phase H Round 6 correction entry): a thin luminous-blue line (with a subtle wider halo underneath and small sampled node markers) connecting first-discovered H3 cells wherever the stored data provides real evidence for it, shown only while a Department is the actual current selection, clipped to that Department's own geometry. **This is explicitly NOT: a GPS breadcrumb trail; the exact road/path travelled; the complete journey; or proof that every connector was physically traversed.** Every point is an H3 resolution-12 cell center (~9-19 m across), never a raw coordinate, paired with that cell's own real, already-persisted first-discovery timestamp (consolidated to one point per physical cell even if separately discovered as both Certified and Non-certified) — recomputed fresh every time, never persisted as a second discovery record, and honestly cell-level-coarse, not GPS-precision — no raw GPS history is stored anywhere in this app (see `docs/ai-context/REJECTED_APPROACHES.md`'s "Persistent raw GPS history" entry, unchanged and not reopened by this feature). A connector between two first-discovered cells is drawn only when the data shows real H3 grid-adjacency between them (not merely a plausible elapsed time and average speed, which alone is insufficient evidence — a cell already discovered on an earlier visit is invisible to this chronology and never bridges two later, structurally unrelated discoveries), AND the gap stays within provisional time/speed guard thresholds. The guiding principle: prefer omitting a questionable connection over drawing a false one — a corridor gap can simply mean "already discovered earlier," not "never visited." Exact colors/widths/opacity/sampling/gap-speed-and-adjacency thresholds are **PRODUCT CALIBRATION REQUIRED**, starting values only. Route-segment Certified/Non-certified styling is an **open product question**, not decided — every segment currently renders in one single provisional blue regardless of the discovered cells' own trust status. A future GPS-precision "actual route travelled" feature would need its own, separate, explicitly-designed privacy-conscious location-history architecture — **ENGINEERING DESIGN REQUIRED / NOT IMPLEMENTED**, not started. **Future, not implemented:** worldwide/Europe geographic generalization beyond this France prototype; overseas French administrative areas; local-discovery-area → H3 navigation below Department; stronger far-zoom visited-country visual prominence; Region-level corridor preview (deliberately out of scope this round — Department-level only, to avoid a cluttered "blue spaghetti" at wider zoom); corridor-segment trust/Certified styling; a future custom subdued/dark/adventure-oriented basemap (see below); an immersive 3D map mode. **PLANNED / NOT IMPLEMENTED — future basemap direction**, confirmed as the approved product direction by physical device testing but not designed or built yet: a much cleaner/simpler, overall darker-gray basemap; discovered/selected geography visually popping from the background; less geographic/text clutter; labels/details progressively revealed by zoom; likely separate Dark and Light modes (the blue route's own luminous styling is deliberately designed with this future dark theme in mind); ocean/background colors still to be designed during that future phase. **NEEDS USER CONFIRMATION:** final art direction and product-specific interaction treatment, including the Region/Department color/zoom-band values above and the route's own calibration values (currently provisional, same status as the existing Country-level constants).

## Progress

## Journey
**PARTIALLY IMPLEMENTED:** destination/module placeholder exists. **DECIDED / NOT IMPLEMENTED:** present discovery as understandable journeys/trips, not permanent raw GPS traces. **NEEDS USER CONFIRMATION:** automatic segmentation, merging, editing, naming, overrides and timeline UX.

## Profile
**PARTIALLY IMPLEMENTED:** profile contains Google/OTP authentication, logout and background-discovery consent UI/disclosure. Consent is distinct from Android OS permission. When foreground permission is absent, the toggle is disabled and an explanatory error is shown. Broader account/settings/privacy/profile surfaces are not implemented.

## Permissions and consent
IMPLEMENTED: background discovery is opt-in and disclosed. Android permission remains the OS authority; persisted consent alone cannot enable tracking. Revocation/downgrade must safely stop effective background tracking. Force-stop is respected.

## Authentication / onboarding
Existing Google Sign-In and email OTP flows exist; consult code/`PROJECT_STATUS.md` for exact current screens. Broader onboarding, first-run education and final account-selection UX are **NEEDS USER CONFIRMATION** when that work is scheduled.

## Empty/error states
**PARTIALLY IMPLEMENTED:** current auth, location-test and permission flows have localized states/copy. No complete final cross-feature specification exists. Use existing resource conventions and request user confirmation only when an unresolved product behavior—not routine UX engineering—matters.
