# Map-matching spike fixture (Phase 2A + Phase 2B) — durable reproduction fixture

This directory is **documentation, not production code**. It exists so a future
developer/session, working only from this repository, can reproduce the synthetic spikes
described in `../MAP_MATCHING_ENGINE_STUDY.md` (Phase 2A: OSRM, Valhalla) and
`../PHASE_2B_BENCHMARK_PROTOCOL.md` (Phase 2B: GraphHopper, now executed) — the exact synthetic
inputs, the exact commands and requests, the exact raw responses received, and the exact
deterministic audit procedure where one exists — without depending on any scratchpad path, shell
history, or conversation history.

## SYNTHETIC SELF-REFERENTIAL REFERENCE — NOT INDEPENDENT GROUND TRUTH

`shared/synthetic-self-referential-route.json` is a real road route on the Isle of Man, but it was
**generated by querying OSRM's own `/route` service** (see `osrm/commands.md` step 6) — the same
family of engine under test. **It is not an independent ground truth.** It exists only to
reproduce: API behavior, sparse-matching mechanics, outlier/index audits, and configuration
experiments. **It must never be used later as the benchmark truth dataset** — see
`../MAP_MATCHING_ENGINE_STUDY.md` §20 for how an actually independent ground truth should be
captured for a real future benchmark (high-frequency independent recording + manual verification,
never one of the candidate matchers).

`shared/input-trace.csv` is the exact 36-point synthetic trace derived from that route (downsampled
to ~500m spacing, with one deliberate dropped-fix gap and one deliberate ~120m off-road noisy
point injected) — see the derivation steps in `osrm/commands.md` step 6. Every request in this
fixture (`osrm/request.txt`, `valhalla/request.json`) was built directly from this CSV's columns.

## Contents

- `shared/input-trace.csv` — the exact synthetic input sequence (index, lon, lat, timestamp,
  radius/accuracy, intent label), shared identically between both engine requests.
- `shared/synthetic-self-referential-route.json` — the raw OSRM `/route` response the trace above
  was derived from (see the warning above).
- `osrm/commands.md` — exact Docker/OSRM commands (pull, extract, partition, customize, server,
  cleanup), with source URLs and version/digest pinning.
- `osrm/request.txt` — the exact, complete `/match` request URL actually executed.
- `osrm/response.json` — the exact, unmodified raw response received.
- `osrm/audit-osrm.ps1` — a small, documentation-only PowerShell script (real JSON parsing via
  `ConvertFrom-Json`, never regex) that cross-references `shared/input-trace.csv` against
  `osrm/response.json` and reproduces the index audit.
- `osrm/audit-result.md` — a precomputed snapshot of that script's output, verified to match a
  fresh run from this fixture alone.
- `valhalla/commands.md`, `valhalla/request.json`, `valhalla/response.json`,
  `valhalla/effective-config-meili.json`, `valhalla/audit-valhalla.ps1`,
  `valhalla/audit-result.md` — the equivalent set for Valhalla, including the exact `meili`
  configuration subset actually in effect (search_radius, gps_accuracy, breakage_distance,
  interpolation_distance, sigma_z, beta, etc. — extracted from the real generated config, not
  invented or assumed).

## Privacy

Everything in this directory is synthetic or derived from public Isle of Man OpenStreetMap data
via Geofabrik. **No personal GPS data, no data from `trip1.txt`/`trip2.txt`/`trip3.txt`/
`vehicle1.txt`/`tracking-calibration.ndjson` (World Discovery's own real calibration artifacts, which
remain local-only and are never copied here), and no path/username information from the machine
this was produced on** is present in any file in this directory — verified by grep before these
files were added.

## Configuration equivalence — NOT NORMALIZED

The OSRM and Valhalla spikes were run with each engine's own defaults (car/`auto` costing) and are
**not** configured to be equivalent to each other (different search-radius semantics, different gap/
breakage-distance mechanisms — see `valhalla/effective-config-meili.json` and
`../MAP_MATCHING_ENGINE_STUDY.md` §17.5). No comparative safety conclusion should be drawn from
these two spikes' differing behavior on the injected point.

## GraphHopper (executed in Phase 2B)

- `graphhopper/commands.md` — exact commands (jar download, GPX conversion, CLI `match` invocation),
  including why the CLI path was used instead of the REST server (the same class of JVM
  loopback-socket sandboxing failure that blocks Gradle's daemon in this environment — documented
  in full there) and the explicit input-fidelity gap (GPX carries no per-point accuracy field).
- `graphhopper/request.gpx` — the exact GPX submitted (derived from `shared/input-trace.csv` via
  `graphhopper/CsvToGpx.kt`).
- `graphhopper/response-default-accuracy40.gpx` / `graphhopper/response-accuracy25.gpx` — the two
  exact raw outputs obtained (CLI default `--gps_accuracy` vs. an explicit `25` to align with the
  other engines' "normal" point accuracy).
- No per-index audit script/result exists for GraphHopper (unlike OSRM/Valhalla) — its GPX output
  does not preserve a clean one-to-one correspondence with the 36 input observations (see
  `commands.md` §4). This is reported as a real finding, not worked around.

No ranking is implied by any of the above — see `../PHASE_2B_BENCHMARK_PROTOCOL.md` for the
benchmark design this now feeds into.
